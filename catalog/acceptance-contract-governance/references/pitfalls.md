# Common Pitfalls（完整版：含失效模式案例）

> 本文件是 SKILL.md「Common Pitfalls」的完整版。SKILL.md 只保留规则摘要；每条规则的典型失效案例见此。

## Common Pitfalls

- 交付物膨胀成多份：记住「一份指令文档」——任务卡/fixtures 回写是执行阶段动作，不是本技能交付物。
- 判据写成散文：「语义相关」「显示正常」= 不可执行；每个模糊词必须有量化阈值或「人工判定」显式标注。
- 在任务书里复制缺陷状态：⛔ 只链接台账条目编号，状态以台账为准（防双份漂移）。
- ID 重排：验收点插入后用下一个空号，禁止重排（对账靠稳定 ID）。
- 探索性项混进完成准则：⏭️ 项不算未完成，但必须在报告注明「无实现」。
- 报告状态误判：含 OMITTED/BUDGET_EXHAUSTED、任一 PARTIAL 或不合法归因时不得 FINAL 系；合法 UNREACHABLE/UNAUTHORIZED/OBSERVABILITY_BLOCKED/获接受 DEFERRED 可签 FINAL-WITH-GAPS，文件名仍为 final-report.md。未裁定 ⏸️ 也进 WITH-GAPS；INTERIM 可 CLOSED，格式失败仍出保底报告。
- 半程收官的反面不是硬上限：全执行≠全✅——⏭️/⏸️/❌ 都是合法终态落判，闸拦的是「连判定都没有」的点，不是拦 FAIL
- 把生成模式当审计用：治理模式才体检既有文档；生成模式对自家产出按六标准自验即可，不做 29119 全量体检。
- 凭据写进文档：账号/口令一律引用密钥源，文档只写角色-权限矩阵。
- 一次性任务书过度拆分：块级指令自包含即可；三件套分离只用于常驻主契约。
- 广度平移冒充深度：从主契约把对应批次点抄过来就叫「重点测」——深度必须来自十一维检查表（test-depth-dimensions.md）的加钻，平移点只解决覆盖。
- 重机制轻功能：安全/边界/并发全绿但正文内容错漏无人发现 = 舍本逐末；D1 内容判定与对比永远先行，「内容显示正确」一句带过不算 D1。
- 脚本化走偏：把「可机判」做成「DB/API 取证优先」——E2E 优先是默认姿态；但「没有 UI」≠「不可验」：机器 persona 的 API/CLI 就是它的入口（`[MACHINE]`），不是辅证。反向的错误同样致命：有 UI 的能力用 API 判定，等于放弃前端缺陷（正确形态：导入上传写「API 操作 + UI 回显」；把无 UI 的归档造数点判 BLOCKED 是错的）。
- 把「没找到通道」当 BLOCKED：涉及入口存在性/可达性的 ⏭️、UNREACHABLE、UNAUTHORIZED 必须先枚举页面/API/CLI并给「不存在/不可用+原因/未授权」结论。BUDGET_EXHAUSTED、OBSERVABILITY_BLOCKED 和纯 DOC 不适用项按各自证明，不伪造通道三选一。**没找过 ≠ 不存在。**
- API 200 当契约过：机器入口点必须断言业务错误码、幂等键、鉴权结果与关键字段，200 只证明可达。实证：同一批请求里，无凭据 200、错误 body 400、重复上传仍 201——只看 200 会把三种语义完全不同的结果都算通过。
- 传输证据只留元数据：下载点只记「文件名+哈希字符串」不落文件本体、上传不留载体副本——跨轮对账时原件已失，证据链断裂（实证：r7 报告 imports/exports 为空被质询「技能问题？任务书不够清晰？」）。修法=传输产物铁律：文件本体入树+清单五要素+对账基准自包含（SUA §2「传输产物」与 §5 自检 #19）。
- 幽灵授权闸：预授权内反复确认会切碎执行，但沉默推定和默认重启同样违规。修法=SUA §1 授权矩阵+本轮显式清单：预授权内连续执行，迟发安全/授权事件只冻结最小作用域，READY 继续。
- 收官闸二态收窄三态：生成时完整内联 SUA 顺序判定，不得把「未触>0 一律 INTERIM」或「未触=0 才可 final-report」写入任务书；INTERIM 优先，其次 WITH-GAPS，最后 FINAL。
- 造数证据冒充判定证据：用 API 造完数据后，判定必须回到该点入口（UI 看呈现，机器入口看契约）；把造数请求的 200 写成该点 PASS 依据 = 自证。

- 有骨架没有灵魂：只交验收点表、不交用户场景——执行者不知道「我是谁、我要干什么」，模拟用户验证退化成逐条打勾。场景建模是工作流第 1 步，不是装饰。
- 垃圾造数：test123/aaa 式数据污染探索判据——真实用户不会造这种数据，系统对垃圾数据的反应不能代表对真实数据的反应。
- 在任务书里留运行时规范指针：「见主契约」「以某版本为准」「执行期以当前版本为准」均违规；交付前按 self-check-gates §4 清零，静态出处/台账/密钥提供方豁免。
- 操作列写「想当然的入口」：只探 API 可达、不验 UI 实况——「新增知识按钮」「分页控件」类前端入口可能不存在，大小限制/默认值文案可能与后端口径矛盾（如任务书写 5MB 边界、UI 声明 50MB）。悬空的批量操作列是任务书最高发缺陷，执行期只能逐点改判并污染报告口径。
- 操作列钉死交互机制而非可观察结果：产品可能用不同机制达成同一结果（如「编辑时勾选创建新版本」实际为每次保存自动版本化）——步骤按「用户做什么→看到什么可观察结果」写，交互路径只作参考示例；反向地，「谁能做」是硬判据：契约声称的能力若对指定角色无任何可达路径（如「创建者 30 天自恢复」只有管理员入口）= 真 FAIL，不许用「存在另一条路径」豁免。
- 造数据量条款不留现场确认口径：写清补数授权、偏差记录和预算；未授权补数只冻结相关 AC，其他 READY 继续，不得放水或全轮停等。
- 以历史任务书/契约或历史缺陷内容为生成基底：一次性任务书只从 PRD/设计/明确承诺、现行侦察和十一维全新生成；台账仅读修复状态、首次发现时间、编号作 ⛔/复验锚，不用历史缺陷内容或分布加钻。既有文档差集仅限独立治理模式，不进入一次性任务书生成。
- 增量补点后计数漏改：点数散落在任务书约十处（头部摘要/范围段/ID 纪律/§3 标题/覆盖表分母/完成准则/汇报模板/产物树/编号范围/回显回合），改点必须同批全改——漏一处=执行者两处口径打架，报告数字对不上账。
- 补丁叠补丁代替干净重出：本技能规程被实质修订后、用户重发同一生成指令=要求按新规程**干净重出**（新文件+头部 supersede 声明指向旧版，旧版保留作留痕不删）——在旧文件上叠三层补丁，文档头部带修正黑历史、执行者友好度差；判断线=修订是否动生成流程（对账前置/密度分档/新增强制节），动流程就重出，小修小补才原地改。
- 答「是否全面覆盖」凭印象：必须走 source-reconciliation.md（穷举需求+四桶归宿+带表结论），取样或只读域名词所在章节必漏散点。
- 对账漏「实装零验收」：以源头功能清单和现行实现做双向扫描，再把每条需求映到本轮新 AC/⏭️/⏸️；禁止读取既有任务书点集做差集。
- 存在性存疑静默处理：源头声称实装但测试侧从未见过实现——存在性确认写进该功能验收点第一步；确认无实现=⏭️+递单登记口径矛盾（勾选 vs 实况两证冲突），不得静默跳过也不得凭空编验收步骤。
- 步骤编号造非常规数字（0 起步/小数步号/负步号）：流程步骤一律纯自然数 1 起顺编；工作流之前的强制条件不占步号，单列「前置闸门」节——非常规编号会被执行者当作可绕过的装饰，一处开口、全库编号纪律失守。
- 规则自我豁免：文字规矩会被执行者窄化解释绕开（实证：把「不得以历史任务书为基底」窄化成「不复制旧点」，随即把两份块书列为「执行单元」继续结构依赖，头部却声明全新生成）——同类纪律必须落成可 grep 的机械闸（见 Verification Checklist「派生依赖清零」「头部声明×正文一致」），劝诫无效、闸才有效。
- 全域书深度缩水三借口禁用：「另派块书所以全局书少写点」「这个域已有深度覆盖」「全局书只做三件事所以只写对账点」——全是基底依赖变体的措辞外壳。域深度只由 PRD 强度+十一维完备度决定；同 PRD 两次生成的全域书实测对照（原型深钻约为后续瘦书的 1.4 倍点数，且瘦书漏 6+ 管理页）证明借口的实际代价。前瞻调度统一措辞「另派块级深化任务书（另派）」，不禁发散。
- 侦察路由未收口：侦察动作本身不等于覆盖——扫出的路由清单是**覆盖义务清单**，逐条落点或 ⏭️/N/A+理由。报表/热图/队列监控/扩展配置类长尾管理页最高频被漏（它们没进用户主线场景，但每条都是真实功能页 + 常带 admin 权限面）。
- 计数机跑少口径就开跑：裸 `grep '^| AC-'` 不分区间会把 §3.x 表头行与判据表引用行一并计入（实证：5 行判据表引用混入→声明 191 被误数成 195，反向把自家零重号书写成重号书）——精确口径=按 §3 标题区间扫描并剔除表头行（命令见 references/self-check-gates.md），顺手用 `uniq -d` 出重号清单。
- 场景表当目录：只写 `场景/persona/目标/关联域` 四列，没有基本/备选/异常流、交接、AC 映射——场景就没有生成力，执行者只能按 AC 表逐条打勾；证据：某轮 50 个 UI 点中 29 个无截图、多个 `[UI]` 写点用 API 直调。修法=场景八要素+场景-AC 矩阵+handoff 矩阵+场景优先执行顺序（self-check-gates §16/§19）。
- UI 点 API 化：`[UI]` 点用 API 200 判 PASS，页面 confirm/alert 未处理、保存后详情/列表未回显；证据：某轮 UI 更正首次被 confirm 默认 dismiss、根本没发请求，申请人保存 200 但详情仍空。修法=GUI 写点真实点控件+处理 dialog+回显并留截图/DOM；TUI/CLI 留终端输出，人类 API 留调用方响应+最终结果。只有用内部/替代 API 绕过既定真实入口才判 PARTIAL/违规，合法人类 API 主证可 PASS。
- DOC 审计冒充 UAT：纯对账不得使用 AC-ID、挂场景、计需求验证分子或出 UAT FINAL；纯 DOC 只能 coverage-audit。
- 域批吞并全部 AC：G-DOM/管理员场景关联全部 AC 只证明矩阵闭合；每个关键业务目标必须有连续基本流、交接和最终用户结果。
- 人类技术入口误标 MACHINE：人类管理员/运维/开发者日常 CLI/API 仍属 UI；MACHINE 仅产品明确交付的机器/外部系统调用方。
- 技术信号直接判 UAT 缺陷：控制台/日志/网络/内部数据先记 TECH-OBS；无 persona 入口承诺失败关联不得形成 UAT ❌。
- 单会话携带长任务 schema：SINGLE_SESSION 不得出现租约/CAS/fencing/多写者接管；只有 EXTENDED_UNATTENDED 才冻结完整扩展契约。
- 缺陷只有技术标题：每条缺陷摘要必须含 persona+业务目标+真实入口+实际/预期结果，技术根因另列。
