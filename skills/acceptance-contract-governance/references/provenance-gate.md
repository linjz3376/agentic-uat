# AC 来源充分性审计（模型自检提示）

> 本文件是**给模型执行的审计提示**，不是脚本。技能本体不依赖 Python/Node/Shell；任何具备阅读能力的 agent 都可用自己的方式核验。外部工具只能作为可选辅助，不能作为交付前提。

## 审计边界

只读当前任务书与当前源：

1. 当前 PRD / 系统设计文档；
2. 当前系统代码；
3. 当前页面 / 路由 / API / CLI 的探知结果；
4. 十一维检查表；
5. 当前缺陷台账（只做风险锚）。

**不要读历史任务书，不要比较旧稿，不要产生“新增/删除/未变/crosswalk/回归重点”分类。** 任务书是当前系统的快照，不是版本差异报告。

## 审计提示（直接交给模型）

你是验收契约审计员。请只基于当前任务书和上述当前源，逐项回答：

### A. 每个 AC 的四类来源

对 §3 每个 AC，检查是否同时具备：

| 字段 | 合格标准 | 失败示例 |
|---|---|---|
| 需求/设计源 | 当前 PRD/设计章节，或当前代码/设计依据 | “旧版任务书”“历史契约” |
| 现行入口源 | 当前真实页面/路由，或 API/CLI 方法+路径 | 只写“接口存在”，没路径 |
| 维度源 | 明确 D1–D11 中至少一维，说明为什么这个深度 | “综合检查” |
| 探针证据 | 生成期实际观察：HTTP 状态、页面文案/DOM、响应字段、代码路径 | “应该可以”“待测”“—” |

输出：每个 AC 一行“PASS / 缺哪一列 / 具体证据位置”。

### B. 来源是否引用历史测试文档

逐条检查来源列是否出现：

- `tests/plans/`、旧任务书、历史契约、旧版任务书；
- `r4`/`r5` 等历史轮次作为来源；
- “沿用/承接/参考旧书”类措辞。

出现即 FAIL，并给出 AC-ID 与原文。

### C. 覆盖矩阵是否闭合

只对当前源清单对账：

1. 当前 PRD/设计需求行 → ≥1 个 AC，或当前 N/A+理由；
2. 当前页面/路由/API/CLI → ≥1 个 AC，或当前 N/A+理由；
3. D1–D11 → ≥1 个 AC，或当前 N/A+理由；
4. 当前缺陷台账 → 只检查 DEF 锚是否挂在受影响的 AC 上，不要求“每个 DEF 一个新 AC”。

输出：源条目 → AC / N/A / 缺口。不要输出“相对旧书新增/删除”。

### D. 点数与证据一致性

- §3 唯一 AC 数 = 头部/范围段/覆盖表分母/完成准则/汇报模板的数字；
- 每个 AC 的四类来源齐全率 = 100%；
- 探针证据不是空话；
- 负向占比、D1 占比按技能基线核对；
- 入口标签 `[UI]`/`[MACHINE]` 逐行互斥、无缺省。

### E. 结论格式

```text
结论：PASS / FAIL
AC 总数：
来源齐全：N / 总数
缺失来源：AC-ID — 缺哪列 — 期望证据
历史测试文档引用：AC-ID — 原文
覆盖缺口：源条目 — 建议 AC / N/A 理由
点数一致性：通过/不通过（差异）
入口标签：UI N / MACHINE N / 缺省 N / 双标签 N
修正建议：按优先级列 1–5 条
```

## 判据条款级追溯（条款级，不是文档级）

**硬要求**：§3 每个验收点的「预期」必须能逐条回溯到 **test basis 条款**——PRD/设计/接口规范的**章节号或条款锚**（不是"见 PRD"这种文档级引用）；产品裁定类口径必须附**裁定日期**。无条款可溯的预期，只能二选一：

1. 标 **⏸️**（挂起待裁定，附已查来源清单）；或
2. 显式标注「合理期待/行业惯例」——该标注即承认它是推断，定级与汇报时不得当作承诺。

**为什么条款级**：文档级引用在执行期等于无引用——同一文档内不同章节的口径可能互相矛盾，执行者会按最近读到的段落判。条款锚 = 可追溯的最小单位。

**来源四态标注**：每个预期的来源必须显式归四态之一——①**来源明确**（条款锚直接命中）②**用户已确认**（产品裁定/澄清回答，附日期与裁定人）③**待确认**（=⏸️，附已查来源清单）④**行业惯例**（=合理期待标注，承认是推断，定级与汇报不得当承诺）。「已确认」与「明确」不得混桶——有人背书的口径和挖到的口径分开记，下轮复用才不致错信。

**审计加法**（provenance-gate E 段输出增列）：

```
判据追溯：AC-ID — 预期 — test basis 条款锚（章节/条款号）/ ⸺ / 合理期待
无锚预期数：N（>0 时逐条给处置）
```

**高频失效模式**（实测复盘）：期望值凭印象写（"应该是 403"），事后发现实现是受理+异步拒绝；把修订记录里的历史口径当现行口径；把标注【下线】当"不可测"而未读后续迭代条目。

## 判定原则

- **功能相同、顺序相同、AC-ID 相同都可以**；只要四类来源和探针证据是当前的。
- **不设“交集为零”**；那是强制差异，不是独立推导。
- **不设“新增/删除/未变”**；没有旧书输入就没有这些分类。
- **不设“回归重点”**；当前未关闭缺陷用 `⛔ DEF-xxx` 挂在受影响 AC 上。
- 点数由当前源矩阵汇总；相同点数可以是收敛，不是罪证。

## 交付前最后一句

如果审计员无法指出某个 AC 的“当前需求源 + 当前入口 + 维度 + 探针证据”，这个 AC 就不应该出现在任务书里；如果当前源清单里有条目没有任何 AC 或 N/A，这份任务书就不完整。
