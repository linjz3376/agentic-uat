## 0. 用户场景与角色（模拟用户验证的灵魂，先于验收点表）

> 场景是生成骨架，不是目录。每个 S-ID 必须有 **基本流 1、备选流 ≥2、异常流 ≥2**；简单域确实无有意义分支时，流可写 `N/A+理由`（占位凑数=返工）；无交接写 `N/A+理由`。**异常流来源 = 异常基线库强制项+建议项（治理侧 references/exception-baseline.md，功能细化后逐功能过库）+ 本轮表 B 特异项；异常状态与恢复至异常前状态必须成对。**不得留空；S0 自由探索除外（可无 AC/流）。场景-AC 矩阵双向闭合后才可写 §3。

### 0.3 页面内容清单（执行期 UI 理解基准，逐涉验页必填）

|---|---|---|---|

**多角色、多账户原则**：模拟用户按场景中的 persona 与实际权限使用对应账户；一个验收轮可以、且在涉及多角色时应使用多个不同权限账户。先列账户别名—角色/权限—用途映射（凭据只从密钥源取，不落文档）；每个场景注明当前使用的账户/角色。验证权限边界时，用低权限角色尝试受限操作，并用有权角色完成其正常旅程；不得借用高权限账户替低权限用户完成操作，也不得把多个角色的权限混在一个账户上后声称各角色通过。只有系统确实是单角色时才使用单账户，并在范围中说明依据。

**造数规范**：测试数据必须像真实用户会造的数据——真实语义的标题/正文/分类（如《2026 Q3 销售复盘》），**禁 test123/aaa/111 类垃圾数据**；真实用户行为本身是探索判据的一部分。
**心智模型判据**：UX 主观项引用用户熟悉的对标产品（网盘/微信/知乎/百度百科…），判据写成「与用户心智模型一致：<对标产品怎么做的>」。

**排除式预授权声明（自主执行边界，必填）**：

| 列 | 内容 |
|---|---|
| **默认授予全集** | 测试消息发送/会话切换/台账写入/排队调度/补测编排/等空闲重启/清场本轮对象——开局无需逐项签，默认全授 |
| **排除清单（恒定，只许加项不许减项）** | secrets 读写/进程裸杀/发布发版/共享数据删除/工作目录外写——开局仅签本清单确认；清单内动作停手等操作者 |

逐项 inclusion 签名废除。临场裁决口径（与执行侧自主推进闸单轴对齐）：**预授权内+可逆=先干后记；不可逆或排除清单内=停手**。**命令即签**：操作者发起测试的命令本身=排除清单默认签署（沉默=GO）；显式附加排除项才二次确认——一个命令发起整批=开局零触点。

**窗口包（owner 资源依赖项必填；本轮无则写「无」）**：先过自助化分级——可自助项（隔离栈=本机独立引擎实例/重启窗=空闲探测自动选窗）必须自助化设计、不得入包；不可自助项（如第二账号）逐项：前置就绪状态+默认窗口建议+预计耗时+消费后清场+**自助化已穷尽举证**（试过哪些自助路径、卡在哪）。窗口包=自助化尽头的容器，不是等 owner 的容器。每项必填「触发器」=自武装一次性挂钟（会话注入等效机制），到点自动消费+登记+通知。

**条件分支条款**：存在性只有执行期侦察才能确定的能力（导出入口/积分入口/独立审核角色…），一律写成条件分支：存在→执行附加点，不存在→记 N/A+理由。两分支都是合法出口，禁止不查就跳，也禁止凭空造点。

## 3. 验收点表
| AC-ID | 向(正/负) | 操作 | 预期 | 回显验证 | 数据源验证 | 门槛 |
|---|---|---|---|---|---|---|
| <按 ac-id-rules.md 编号> | 正/负 | <`[UI]` 或 `[MACHINE]` 开头，再写可直接执行的命令/路径> | <可机判预期；模糊词→§4 判据> | <刷新/换页/换账号确认；机器入口写副作用可见位置> | <DB/文件/缓存直查，仅辅证> | <⛔ 链接台账编号 / ⏭️ / ⏸️ / -> |

> **入口标识**：操作列首令牌必须且只能是 `[UI]`、`[MACHINE]` 或 `[DOC]`。`[MACHINE]` 仅用于「该能力无 UI 入口」或「persona 是机器身份」；须写契约断言（状态码/业务错误码/幂等键/鉴权/关键字段）。`[DOC]` 仅限不发起产品交互的覆盖对账点。有 UI 的能力不得用 `[MACHINE]` 代替用户旅程；内部接口/DB/日志只能进「数据源验证」列作辅证。
> **UI 步骤脚本**：`[UI]` 写点必须写实际控件标签、confirm/alert/prompt 文案、保存后的详情/列表回显；只写「填表保存」=不可执行。UI PASS 必须有判定时截图/DOM；API 响应只能辅证，不能单独判 UI 点 PASS。
> 「向（正/负）」列为标准列（全域轮强制；窄域小任务可省略维持六列，省略时交付回执的负向占比须人工点数并注明）。负向占比机跑命令见 references/self-check-gates.md。负向用例必须挂正向基线：无正向基线的点记 ⏭️ 不适用+通道结论，不计入负向占比分母（1.5.30）。

## 6. 执行者手册（任意 AI agent 拿到本文档即可执行，设计基线）

### 你是谁
你是 §0 的 persona。全程以该用户的心智操作：他想完成什么、他看到什么、怎样算成功/受阻。**遇到文档没写的情况，按「真实用户会怎么办」处理并记录**——你不是逐条打勾的机器人。

### 用什么操作
使用执行环境可用的浏览器或桌面交互方式（人工操作、自动化工具均可，工具名称仅为示例）。按产品实际入口导航，按**用户可见标签**操作，不依赖只有开发者能看到的内部选择器。多角色账户使用独立浏览器上下文/profile 或等价隔离方式，防止会话串用。**拟人操作纪律**（出处 simulated-user-acceptance §2）：必须用真实事件操作（点击/输入/选择/键盘），禁止把「打开页面+截图」当操作；每个操作后必须验证可观察变化（页面变化/网络请求/下载事件/弹窗），无变化记「操作无响应」转缺陷候选；prompt/confirm/alert 必须真实处理双路径；读到的链接 href 直达仅限「同目标等效」且在日志记理由。

### 浏览器能力清单（开工环境闸的一部分，缺项即记）
执行前先确认所选浏览器工具具备以下能力，逐项实测打勾：①打开 URL 并等待网络空闲/元素可见（等待策略：等「预期元素出现」而非盲等固定时长）②真实点击/输入/选择 ③**判定时截图**（evidence/<AC-ID>/ 命名，判定同时刻留存，事后补图只能标「事后补证」）④捕获下载事件（文件名+字节数）⑤处理对话框（prompt 可输入、confirm/alert 可辨识）⑥读页面文本/DOM。缺某项：受影响控件记「有意跳过+浏览器能力缺口」，并在报告能力缺口节声明——**不得因工具缺某能力就静默跳过或改判**。若发现产品依赖浏览器基础能力而该工具不支持（如 prompt() 不支持），**静默失败本身是缺陷候选**——记「弹壳/无响应」进缺陷库（r7 实证：预览/下载在 prompt 不支持的浏览器里静默失败，用户零提示）。

### 执行规程
1. §2 环境自检 → GO/PARTIAL/NO-GO
2. 台账核对：头部「缺陷台账快照」行核对 ⛔ 门槛依据；**台账不可达 → 按该快照行的生成日决策，并在报告注明「台账不可达，按快照日期决策」**
3. 逐场景走 §0 旅程（⛔/高风险场景优先）：每个场景先基本流，再 ≥2 备选流、≥2 异常流（N/A+理由除外）；完成挂靠的 §3 验收点：UI 观测判定 → 截图/掐表取证 → 记录 ✅/❌/⏭️
4. 判定纪律：有辅证无 UI 判定 = 未验；唯三可跳（⛔ 未修 / ⏭️ 无实现 / ⏸️ 口径挂起只实测记录）；禁止假装通过。UI 写点必须真实点按钮、处理 confirm/alert/prompt、记录保存后回显；API 直调不算 UI 点通过。**控件级覆盖**：每个涉验页面的每个可操作控件真实操作 ≥1 次并登记控件操作矩阵（页面×控件×动作×操作后观察结果×证据）；只加载不点算漏测；写控件受载体/授权约束记「有意跳过+理由」；报告前按完成准则的控件覆盖闸机验
5. 场景走完后按域做 AC 回归（域顺序只用于回归，不替代场景顺序）；每个 AC 的终点写回场景日志。
6. ❌ → 十段式缺陷（用户语言）；证据落盘（§5 完成准则的落盘结构）
7. S0 自由探索 10 分钟，记录皱眉时刻；全域轮 G0 20 分钟
8. 每场景一句场景级结论 → 七段式汇报 → 按 Final-Report-Gate 选择 final-report 或 interim-report

### 凭据
本文档零明文。按 persona/角色使用一个或多个对应测试账户；每个账户别名对应其获准的密钥源引用或执行环境凭据项，具体注入方式由执行平台决定，不假设固定变量名。**不得要求整轮只用一个账户**；也不得跨角色借用高权限账户。所需账户/凭据缺失时，仅阻塞依赖该角色的场景/权限点，其余不受影响；若认证链整体不可用则按 §2 总闸 NO-GO。禁止猜测或硬编码凭据。

### 用户知识与证据边界
以该 persona 通过产品实际提供给其使用的入口（UI、机器入口 API/CLI 或其他产品界面）观察业务结果。源码、数据库、日志、监控和内部接口只能作定位或本质不可由该入口观察项目的辅证；不得用它们替代用户侧判定。若必须经管理/运维通道准备测试数据，任务书须预先列明授权和范围；该准备过程不算普通用户能力验收。机器入口点按契约断言判定（状态码/错误码/幂等/鉴权/字段），接口 200 不等于通过。

### 你不需要
不需要任何外部技能、记忆或培训；不需要访问本文档之外的任何版本化文件。

## 7. 缺陷流转
缺陷登记/跟龄/复验走 <项目> 指定的缺陷台账或跟踪系统；执行任务的状态按项目可用的任务跟踪方式记录。若没有专用任务跟踪工具/流程，将进度与缺陷编号记入报告并链接台账；不依赖某个特定技能或供应商工具。

## 8. 异常处理 SOP（执行期遇阻的统一处置，供 §6 引用）
| 异常 | 处置 | 记录位置 |
|---|---|---|
| 环境断连/健康检查转红 | 停止新增用例，已验点结论保留并注明断连时刻；复连后对受影响点重验 | 汇报 §偏离 |

| 入口不存在/文案与预期矛盾(非缺陷级) | 按 §2 条件分支条款记 N/A+实际观测；判据真值受影响的点如实 ❌ 或 ⏸️ | 场景结论+验收点表 |

| 凭据不可用 | **停止并请求操作者提供，禁止猜测/硬编码** | —— |

| 执行中数据被其他用户改动 | 不清理他人数据；暂停受影响点，核实归属并在授权测试数据上重跑；无法隔离时记 ⏸️ | 验收点备注 |

## 9. 汇报与缺陷格式（常用节，按块裁剪；供 §5/§6 引用；自包含铁律要求随文档内联）

**七段式汇报**（每场景一草稿→汇总报告；**Final-Report-Gate 三态：未触=0 方可出具 final-report.md；未触>0 且全部 UNREACHABLE/DEFERRED（有证据/接受）→ final-report.md 标 FINAL-WITH-GAPS；存在未补做 OMITTED 或 UI 证据覆盖<100% → interim-report-<date>.md**——以执行侧 §8.2 当前版本为准）（条款快照·出处 simulated-user-acceptance §8.1 汇报内容/§8.2 报告状态，执行期以其当前版本为准，冲突记偏差提交裁定）：①头部=任务 ID+环境 GO 判定+纪律声明+覆盖度量三行（需求覆盖率/UI 证据覆盖率/未触率，机算，口径以 acceptance-contract-governance references/coverage-metrics.md 为唯一权威）②场景级结论（每场景一句「作为 persona，能/不能完成业务目标」）③S0 皱眉时刻清单（分级）④验收点统计（✅/❌/⏭️/⏸️ 分类计数，数字与 §3 表逐项对得上）⑤缺陷清单（编号+粗粒度影响，细则见十段式）⑥偏离与快照决策记录（台账不可达/环境降级等）⑦结论=总体判定（收官 GO/带伤 GO/NO-GO）+必改项。

**十段式缺陷**（每个 ❌ 一条，用户语言；条款快照·出处 simulated-user-acceptance §7.1/§7.2 与 reference/defect-classification.md，执行期以其当前版本为准，冲突记偏差提交裁定）：①缺陷编号（同台账）②标题（用户视角一句话）③严重级别+用户场景 ④复现步骤（产品入口路径+可见文字标签）⑤预期结果 ⑥实际结果（含用户侧证据路径）⑦证据（截图/录屏；必要时附内部取证并标「辅证」）⑧初判根因（可缺省，标「待研」）⑨评分依据 ⑩登记号与复验口径（链接台账条目）。

**产物树**（随 final-report.md 交付；执行侧细则以 simulated-user-acceptance `reference/artifact-conventions.md` 当前版本为准）：

├── interim-report-<date>.md # INTERIM 窗口报告（与 final 二选一）
