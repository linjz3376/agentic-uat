# 验收契约与测试任务指令文档治理（Acceptance Contract Governance）

## Overview

**技能目标**：**高覆盖面的测试验证点执行指令**——
- **高覆盖面** = ① **test basis 穷尽**（硬闸）：四活源推导（PRD/设计文档横切 + 缺陷台账【仅修复状态/首现时间/编号】+ 现行 UI/端点侦察 + 十一维加钻）落到三份可点名清单——需求行无孤条、路由/入口无 MISSING、深度维度无空洞；② **行为空间不追求穷尽**：等价类抽样（D2）与 golden set 锚定是合法设计，禁止以「没测完所有输入组合」为由返工或虚报；③ 覆盖度量**只报数、机验口径一致，不设及格线**——需求归宿分布与三度量（需求覆盖率/UI 证据覆盖率/未触率）的口径唯一权威为 `references/coverage-metrics.md`。禁以历史任务书/契约为基底——派生叠派生=误差复利，见生成模式素材原则；
- **测试验证点** = AC-ID 化、可机判、每点带**入口判定路径**的验收点表（任务书主体）——入口为 `[UI]`（用户页面）或 `[MACHINE]`（该 persona 的产品机器入口：API/CLI/客户端），二者必居其一；
- **执行指令** = 自包含单文档（判据表/执行者手册/降级路径内嵌），任意 agent 零追问直接执行模拟用户深度验收。
- 口径优先级/边界条款执行时不得放宽；版本演进历史见 references/changelog.md，正文不内联版本标签、不作过程叙述。

**双模式技能**：
- **生成模式（主）**：把「重点测试某功能」的需求变成**一份自包含的可执行指令文档**——交付物只有它，拿到就能跑，执行 agent 无需再追问。
- **治理模式（辅）**：对既有验收契约（常驻文档）体检、清历史污染、做 29119-3 三件套拆分。

**形态原则（复用次数决定形态）**：常驻主契约服务多轮 → 设计/规程/数据三层分离防漂移；块级任务指令服务一轮 → 自包含单文档降低执行摩擦。任务书里可复用的部分（新端点/探针/AI 判据条目）执行后回写 fixtures/playbooks，成熟的新验收点递单回流主契约。

## 核心定位：为「模拟用户验证」而生

本技能的一切产出服务于一个目标——**让执行者以真实用户的身份完成业务旅程，并作出用户视角的判定**。验收点表是审计骨架，不是执行形态；执行形态是**用户场景**：谁在什么动机下走什么旅程，每一步看什么、期待什么、怎样算受阻。

三条灵魂判据（每份交付物自答）：
1. 执行者读完知道「我是谁、我要干什么、完成长什么样」（角色+业务目标+旅程）
2. 每个判定都能回答「真实用户此刻会看到什么、会怎样反应」
3. 缺陷描述用用户语言（「我收藏的知识找不到了」）而非系统语言（「缓存未失效」）

**机器身份也是用户**：客户端、集成服务、导入代理、运维脚本没有页面，但它们是产品明确交付的使用者，其真实入口就是 API/CLI。对这类 persona，按契约与可观察结果判定，不因「没有页面」降级为辅证。

## When to Use

- 用户说「重点测 XX 功能」「给 XX 安排一个测试任务」「出一份 XX 的验收/测试指令」「出任务书/测试计划」——范围词路由：模块名→块级模板；「全项目/全域/跨模块/全流程/全面深度测一遍」→全域轮模板（project-instruction.md）。拿不准时按全域轮处理，并在回执中说明范围判断
- 用户提供 PRD 章节/口述标准，要求转成可执行的验收点
- 用户问「N 个验收点是否已全面覆盖/够不够全」→ 触发完整性背书规程（references/source-reconciliation.md），穷举源头需求行逐条归类后才可下结论
- 用户点名**验收契约**（常驻文档）要求治理：体检、清历史状态、按 29119-3 拆分、迁移到新项目——指令须含「验收契约」锚，纯「清理/评审/审计 XX」无此锚不归本技能

**不用**：本技能负责生成任务指令，不负责实际执行。执行者按任务书内嵌手册跨平台执行；`simulated-user-acceptance` 可作为通用执行指南（若可用），不是执行前提。任务/缺陷闭环、无人轮审计和自由探索可使用相应流程；这些流程或技能不可用时，按任务书内嵌的自包含规程继续，不因本机缺少特定技能而阻塞。

## 生成模式（主）

### E2E 手工优先原则（功能测试的默认姿态）
默认验证姿态 = **模拟真实用户的端到端测试**：从该 persona 实际可用的入口出发完成业务旅程，按其可观察结果判定。五条规则：
1. **可机判 ≠ 必须脚本化**——判据必须能被人「看页面」或按机器入口契约判定（阈值类用户可掐表：≤3s/≤2s）；只有当判据**本质不可由该入口观测**（审计字段、索引时延、孤儿对象、并发计数）时，才允许 DB/日志/内部接口取证，且只能定位为辅证，**不替代入口侧判定**。
2. 验收点表「回显验证」列每点必做；「数据源验证」列是可选辅证列，不是每点必做。
3. **人工判定是合法出口不是偷懒**——主观项（排版/文案/推荐相关性）显式标「人工判定」并给核对要点清单，禁止用 DB 结果反推页面通过。
4. 禁止「脚本绿 = 功能过」——接口 200 只证明可达，不等于契约正确、更不等于用户旅程通过。
5. **入口二分（取代「API 一律为辅证」的旧口径）**：
   - 产品交互点的主入口只有两种：`[UI]` 用户页面，或 `[MACHINE]` 该 persona 的产品机器入口（API / CLI / 客户端）。
   - `[MACHINE]` 仅当满足其一才合法：① 该能力**没有 UI 入口**，产品就是按机器入口交付；② persona 本身是**机器身份**（Windows 客户端、集成服务、导入代理、运维脚本）。
   - **有 UI 且 persona 是人 → 必须 `[UI]`**，不得用 API 代替用户旅程；同一能力两套入口都在时，UI 判呈现与内容，机器入口判契约一致性，两者都要落判。
   - `[MACHINE]` 点按 L1/L2/L3 正常判定、**不标「辅证」**，但必须写契约断言：状态码、业务错误码、幂等键、鉴权结果、关键字段、副作用在何处可见。
   - **管理端 API 是有效执行，业务触发链路分开标注**：管理端/运维类写入接口（如订单状态修改、结算明细修改）是产品既有机器入口（persona=管理员/运维），其调用属有效执行证据；但须与「业务事件自动触发的链路」分开标注触发方式，不得混算为同一类构造。
   - **入口存在性侦察优先序**：判定某能力是否具备机器入口，按 ①**契约侦察**（OpenAPI/Swagger 文档、网关路由注册、服务目录、后端路由装饰器/Handler 映射）→ ②**调用链路侦察**（前端请求封装层、代理/网关转发配置、浏览器 DevTools 或 HAR 抓包精读的接口调用）→ ③**通道结论**（仍不可得时按三选一落结论：通道不存在 / 存在但不可用+原因 / 存在但未授权）的顺序取证。前后端分离只是 API-first（契约先行）交付模式的常见形态，**不是接口存在的证据**；管理端页面可观测的写操作至多算「存在性高概率线索」，须经 ①或 ②实证后方可计为有效执行入口。
   - **`[DOC]` 窄豁免**：仅用于不向产品发起任何交互的覆盖对账/文档核对点（如「源头需求逐条归宿」「路由→AC 映射」）。`[DOC]` 点不得改成产品功能点，也不得作为跳过产品验证的出口。
   - 内部接口、DB、日志、源码**永远不是入口**，只能进「辅证」列；`[AUX]` 不允许作为任何验收点的主入口。
   - 禁止用管理员内部接口冒充普通用户入口；机器身份必须用它自己的凭据，不得借用管理员 Token 代判。

### 场景生成力闸

**机械闸（缺一即返工）：**

1. **场景八要素**：每个 S-ID 必须有 `persona / 动机 / 业务目标 / 入口 / 基本流 / 备选流≥2 / 异常流≥2 / 交接`；流可写 `N/A+理由`（占位凑数=返工）；无交接写 `N/A+理由`，不得留空；S0/G0 自由探索除外（可无 AC/流）。
2. **场景-AC 矩阵**：`S-ID × AC-ID` 双向映射；每个 AC 至少挂 1 个 S-ID；每个 S-ID 至少挂 1 个 AC；S0/G0 自由探索除外（可无 AC）。映射并集必须等于 §3 主表全集，差集=返工。
3. **handoff 矩阵**：跨角色/跨块场景必须写 `从 S-ID/角色 → 到 S-ID/角色 | 对象/状态 | 入口 | 期望`；没有交接记录=场景没走完。
4. **执行顺序**：任务书 §6 必须写“按 S1→Sn 场景执行（⛔/高风险场景优先），场景内基本流→备选流→异常流；域顺序只做 AC 回归”；写“按域顺序执行”=场景降级，返工。
5. **UI 步骤脚本**：每个 `[UI]` 写点必须写实际控件标签、confirm/alert/prompt 文案、保存后的详情/列表回显；只写“填表保存”=不可执行。
6. **G0 模板**：全域 20min/块级 10min；四栏笔记（观察/疑问/缺陷/覆盖）；产出新增 B 点/缺陷/未覆盖；G0 不是 checkbox，是执行场景。

**场景点遗漏的高频区**（生成时逐条核）：角色交接（导入→复核→归档→抽样→审计）、失败恢复（识别失败→人工复核→重传）、审批回退（manifest 404→手工归档/恢复）、抽样闭环（计划→任务→打标→问题/通过→统计）、跨块追踪（任务→发票→目录→修改记录/审计）、双角色隔离（管理员 vs 普通用户 vs 审计只读）。

### 前置闸门：目标项目确认与源头新鲜度核验

- **目标必须明确（多项目并存时禁止凭上下文默认值拍板）**：生成前先枚举项目区候选（如 `ls <项目区>/`；PowerShell 等价 `Get-ChildItem <项目区>`），用任务性质信号逐项匹配：① 用户指令/上下文是否显式点名 ② 项目内是否有需求源头文档（PRD/设计）③ 是否有测试基建与活跃台账（tests/ 树/缺陷台账）④ 本机上下文文件锚定的质量/测试归属域。**唯一匹配→继续；≥2 个候选同时匹配且用户未点名→按澄清问题协议回问（业务语言+≤3 选项+写明默认项），禁止静默沿用会话默认值**——「我一直做这个项目」不是判据，是惰性。产出文档头部写明项目名与来源文档名。
- **新鲜度是实测值不是默认值**：源头文档（PRD/设计）以版本控制为准——生成前 `git fetch` + 核对 `HEAD..origin/<主分支>` 落后提交数与源头文档 diff（或等效 VCS 操作）；落后→先同步到最新，或在文档头部声明「基于 <commit 短号/日期> 快照」；无版本控制的源头→记文件 mtime 并写入头部声明。判据同判定锚纪律：新鲜度每轮当场核验，禁止凭「上次拉过」推定。
- 无 N/A：拉不到远端（离线）→头部声明离线快照日期后继续，报告注明。

### 造数通道盘点（先于一切「无法验证」结论）

生成与执行都必须在写点、判 BLOCKED 之前，盘点**能进入被测系统的通道**，并随交付附一张表：

| 能力 | 通道（页面 / API / CLI / 客户端） | 可用性 | 授权与范围 |
|---|---|---|---|
| <如：造归档发票> | `POST /api/v1/import-tasks/{id}/historical-commit` | 可用 / 不存在 / 不可用（原因） | <本轮是否获准> |

判据：
- 判 `BLOCKED` 或 `⏭️` 前必须给出结论三选一：**通道不存在** / **存在但不可用**（附具体错误或原因）/ **存在但未授权**。
- **禁止把「我没找到」写成 BLOCKED**——写接口、CLI、页面入口都要主动枚举（路由装饰器、CLI 命令、前端导航），而不是凭印象。
- **造数通道 ≠ 判定通道**：用 API/CLI 准备数据合法，但造数动作的返回码不得作为该点 PASS 依据；造数必须登记前缀、归属与清场债务。
- 造数通道需要改动远端配置或重启时，视为**未授权**，不得自行开启；只能记为待授权或改走本机隔离栈。

### 自主执行优先设计闸（执行形态基线）

任务书的默认执行者 = **无人值守的 AI agent**（自主执行是设计目标，不是执行期的即兴发挥）。落笔前必须过这道闸：

1. **通道优先序（E2E 拟人操作为核心）**：同一验收目标存在多种执行通道时，按「**①真实入口拟人自动化（核心）**——按被测产品的真实用户入口选型驱动通道并同步操作之：浏览器类→DOM/Playwright 自动化；桌面客户端类（聊天/邮件/办公等）→坐标点击/键入/剪贴板粘贴/剪贴板回读/判定时截图自查（Chromium/自绘 UIA 裸树时依然成立）；其他入口以此类推。**拟人四要素恒定**：真实事件操作、动作后验证可观察变化、判定时留证、全程零人工。PC QQ 只是聊天客户端类的一个实例，非本原则的范围边界。**②产品自带测试注入端子/平台协议模拟驱动器**（机器 persona 通道，作辅证与不可 UI 化项的补充）③真人操作（仅平台物理强制项，如平台只接受真实客户端回调的特定交互）」排序选点；平台类约束必须在生成期用一条端到端探针**实证或证伪**，禁止把关键假设留给执行期首发现——平台类假设错误是驱动器返工与批量人机中断的高发根因。驱动器实现属项目侧资产，技能本体零实例（可移植红线）。
2. **人机协同项前置压缩（单次批量）**：确需真人的点，全部登记进任务书 §2「开局人机批次表」（**T+0 批量**=开局 3 分钟内一次做完的动作全集/媒体包/群 setup；**T+0 观察期**=截图清单≤5 张或 payload 主证声明；**预授权池**=env/重启/台账写入一次性签；**兜底**=缺做降级处置），**总量 ≤2 个时点，超时任一时点=生成返工**；禁止设计成边跑边要。任务书 §2 必内嵌两物：**排除式预授权声明**——**默认授予全集**（测试消息发送/会话切换/台账写入/排队调度/补测编排/等空闲重启/清场本轮对象），**排除清单恒定**（secrets 读写/进程裸杀/发布发版/共享数据删除/工作目录外写）——开局只签排除清单确认，逐项 inclusion 签名废除（三档声明保留为溯源视图，临场裁决不按档回想）；与**窗口包**——凡依赖操作者资源的项先过**自助化分级**（见第 5 款），不可自助项才准入包：一次消费包=前置全就绪+默认窗口建议+预计耗时+消费后清场+**自助化已穷尽举证**（试过哪些自助路径、卡在哪）。**命令即签语义**：操作者发起测试的命令本身=排除清单默认签署，沉默=GO——一个命令发起整批=开局零触点；仅当操作者显式声明附加排除项时才二次确认。
3. **载体不可达预改判**：生成期即确认执行载体形态（桌面客户端可否被自动化驱动、UIA 可用性、多开能力）；载体不可达的 [UI] 点在生成时就完成入口改判（机器通道重设计或 ⏭️/UNREACHABLE 预登记+三选一通道结论），不得留给执行期临场发现。
4. **环境还手预判**：被测系统带自动拉起/看门狗/单实例锁时，任务书必须预写「测试替身接管规程」（停用谁、抢锁失败重试几次、如何复原），禁止执行期 improvising；**拟人自动化额外要求**：操作者共享桌面时必须预写「清场窗口或独立会话」二选一并获操作者确认——共享桌面下坐标自动化与真人操作相撞是实测高频事故。

5. **资源依赖自助化分级**：依赖操作者资源的验收前置（重启窗/第二账号/隔离栈/停机）禁止裸进人机批次表——先过自助化分级：**可自助项必须写成自助化设计**（隔离栈=本机起独立引擎实例、重启窗=空闲探测+自动选窗+预授权消费），不可自助项才准入窗口包且必附自助化已穷尽举证。判定口径：窗口包是「自助化尽头的容器」，不是「等 owner 的容器」。窗口包每项必填「**触发器**」=自武装一次性挂钟（**任务注入等效机制**——向执行体所在会话投递一条到点自动执行的指令；载体无关：CLI 型执行体用其 headless 一次性调用形态，IDE/客户端型用其脚本/自动化接口，要求可迁移可复制；示例：`opencode run -s <会话> "按断点继续" --auto` 是其中一种载体的形态，非规范本体）——到点自动执行消费动作+登记+通知，操作者是被通知对象不是执行者。

**删除阀登记**：①不替代「E2E 手工优先原则」——该原则管**判定姿态**（以用户视角与可观察结果判），本闸管**执行形态设计**（谁来按、怎么按），二者正交；②失效条件：当目标产品普遍提供官方测试注入通道成为生态惯例、且平台模拟驱动器可由 fixtures 标准化复用时，本闸第 1 条的通道优先序部分进退役评审。

### 素材自挖原则（用户只出意图）
生成任务书所需的现状素材由 agent 自己挖，**不向用户要清单**：「测什么/不测什么」「前端路由有哪些」「端点有哪些」都是 agent 可自挖的事实——读 PRD/设计文档、缺陷台账，实测页面路由与后端端点（测试侧可读范围见下方目录白名单）。用户只给意图（模块名+「更全面/重点测 X」类方向），理解诉求→挖素材→生成 prompt→产出文档全归 agent，过程中不向用户回填选择题。只有挖不到且影响判据真值的口径缺失才回问；挖得到的一律不问——把自挖清单当问题丢回用户=把 agent 本职推回给用户。

**生成期素材目录白名单（机械规矩）**：生成任务书时可读的测试侧内容**仅限缺陷台账镜像 + 缺陷队列表（bugQueue）**——缺陷是实测锤出的一手事实，四活源之一。台账镜像**动态定位**：扫描 `<项目>/tests/reports/` 下现存的缺陷台账文件（按 defect/tracker/缺陷 语义识别，一份为准；多份并存须先对账合并再引用，禁止凭文件名猜）。`tests/plans/`（历史任务书）与 `<项目>/tests/reports/` 下的执行产物目录（`<日期>-*/` 形态，动态识别而非枚举名单）**目录级禁读**——派生产物不因其在 tests/ 下就变成事实源。判据一句话：内容属于「谁的实测事实」还是「哪次生成的说法」；但执行按目录一刀切，不按性质个案判断（性质判断留解释口子）。**夹具例外**：`<项目>/tests/fixtures/` 下的数据/夹具/golden 文件**可读**——夹具是执行资产与实测沉淀物，不是口径基底，复用不构成基底依赖；AI/LLM 类判据生成前**必查该目录现有 golden set**：存在即复用其断言结构写进验收点（机判），未建才降级「人工判定」并显式注明「golden set 未建」。fixtures 目录内的任务书/报告/契约类派生文档仍按派生产物禁读。**可移植红线：技能本体与产出文档零实例残留——项目名/文件名/目录名/主机/账号/ID 一律占位符或动态扫描，实例专有命名只准出现在本机上下文文件，不进技能、不进任务书（changelog 历史区豁免：旧条目中的路径/邮箱仅作留痕，不作现行口径）。**

**生成基底=四活源全新生成，禁以派生产物为基底**：每版任务书从 ① PRD/设计文档横切（**覆盖范围唯一来源**）② 缺陷台账 ③ 现行 UI/端点侦察 ④ 十一维加钻 **重新生成**；旧版任务书/历史契约=派生口径，只留痕不作基底。派生叠派生=误差复利（两次实证见 references/pitfalls.md「以历史任务书为基底」条）。**历史参考白名单**：对历史轮次唯一合法引用=缺陷台账条目的 ①**修复状态**（⛔ 放行/回归判定）②**首次发现时间**（龄期/上下文）③**编号**（⛔ 挂链/复验锚）。禁止以历史缺陷内容或历史缺陷分布做设计输入（加钻只由 PRD+十一维+现行侦察推导）。历史任务书/历史报告/历史证据目录级禁读（生成期已有，**执行期同禁**：本轮判定只看本轮任务书+本轮实测）。**每轮全部重新执行**。

**挖掘顺序=需求源头优先**：产品需求文档/系统设计文档是**需求源头**，测试契约/历史验收指令是**派生口径**——以契约为基底必须回 PRD/设计文档对账，防继承契约盲点。规程：①挖素材第一步动态定位需求源头文档（在 `<项目>/docs/` 等目录扫描产品/设计类文档，禁止写死路径，以实际找到的文档名为准）并摘出被测域全部需求条目 ②契约/历史任务书点与需求条目逐条对账，契约有而 PRD 无=存疑标注，PRD 有而契约无=必须补点 ③两源冲突（如恢复权限口径）不猜，标 ⏸️ 递单裁定。规程全文见 `references/source-reconciliation.md`——对账摘要（补点/存疑/冲突各几）必须写进任务书头部来源声明。**无源头文档分支（降级路径，基底红线不变）**：`<项目>/docs/` 等动态扫描无果→①现行 UI/端点侦察升为主源，行业惯例/用户合理期待补源——「不得以历史任务书/契约为基底」禁令不变 ②头部显式声明「无 PRD 基线·覆盖口径降级」，需求归宿分母=侦察+惯例条目 ③禁止无声明裸跑。规程全文见 source-reconciliation.md「无源头文档降级规程」。

**澄清问题协议（向用户回问的纪律）**：默认用户非技术、只说得出意图，回问是最后的口子不是工作方式——**三条件同时满足才问**：①口径影响判据真值（不问会产生错误 PASS/FAIL）②PRD/设计/实测/台账全部自挖无果 ③答案无法靠执行期实测记录兜底。怎么问：业务语言一句话（禁术语）+ 选项 ≤3 个 + **默认项写明「不答则按 X 执行」**；一轮最多 3 问；问完立即继续不停等。示范（恢复权限双源冲突的正确问法）：「删掉的文档谁来恢复？A 只有管理员 B 作者 30 天内自己也能 C 定不了就两边都记录、暂不定谁对（默认 C）」——错误示范：「PRD V2 §3 与契约 AC-02-005 口径冲突，请裁定」（术语堆叠=把工作推回给用户）。

### 工作流
1. **场景建模**（灵魂步骤，先于一切）：按「场景生成力闸」产出 S-ID 八要素（persona/动机/目标/入口/基本流/备选流≥2/异常流≥2/交接）、场景-AC 矩阵、handoff 矩阵；全部验收点必须挂靠 ≥1 个场景，孤儿点不许存在（纯机制点归入「管理员/运维用户」场景；全域轮深度点按**域批挂靠**——每域一条域批场景承接该域全部深度点，跨块旅程只收 ≥2 块穿过的主线点，见全域模板 §0）。交付文档以场景矩阵开篇，验收点表紧随其后。**异常流来源 = 异常基线库强制项+建议匹配项（见 references/exception-baseline.md，功能细化后逐功能过库，强制档满足触发条件不得跳过）+ 表 B 项目特异项；异常状态与恢复至异常前状态必须成对——只测触发不测恢复按漏项计。**
2. **需求解析**：PRD 章节 / 用户口述 / 端点探测 → 逐条可核验条件；有歧义当场澄清，不猜。
3. **覆盖依据表先行（scope-first，先于验收点表落笔）**：每域一行「域 → PRD 章节/FR 号 → 计划点数 → 来源类别（PRD 横切/侦察加钻/十一维）」——scope 由本表锁定后才开始写验收点；写点过程中任何「这个域有/没有块书」式的存在性判断一律无效，覆盖只认 PRD 出处。表随交付。**路由→验收点全覆盖（全域轮强制）**：侦察到的每条前端路由/管理页/常驻入口必须落在该域 ≥1 个验收点，或显式 ⏭️/N/A+理由写进覆盖表——长尾管理页（报表/热图/队列监控/配置中心/扩展集成页）是最高频漏点，静默缺席=「实装零验收」变体。
4. **深度设计**（「重点测」强制）：走十一维检查表（references/test-depth-dimensions.md）——**D1 功能正确性（内容判定与逐字段/逐元素对比）永远先行，占比按域类型分档**（密度基线见 references/test-depth-dimensions.md：内容型 ≥40%/防线型 D1≥15% 且 D3+D9≥50%/流程型 D1≥25% 且 D5≥20%），其余十维（边界/权限矩阵/并发时序/状态机/失败注入/一致性量化/性能/安全/可观测性/体验兼容）系统排查；每维产出验收点或显式 N/A+理由；负向占比 ≥30%；**负向用例必须挂正向基线**：无正向基线（无法建立 PASS 参考）的点不得记负向，只能 ⏭️ 不适用+通道结论（不存在/存在但不可用/存在但未授权），并从负向占比分母剔除；**覆盖表在生成时即回填真实 AC-ID——留白交付=深度设计未走，直接返工**。这张表是暴露深度空心的自检机制：D1 行若只填得上数量核对类 AC（数了几个标题/表格/图片），说明元素顺序/位置、渲染真显、AI 回填内容真值、格式元数据多端一致性没设计验收点——当场补钻，不许等执行期或评审时才被发现。交付附深度维度覆盖表。
5. **验收点推导**：列表成表——每点含 AC-ID + 入口标识 + 操作（可直接执行的命令/路径）｜预期（可机判）｜回显验证｜数据源验证（可选辅证）+ 门槛标注（模板见 templates/task-instruction.md §3 列结构，其含标准「向（正/负）」列构成七列——全域轮强制采用，负向占比从人工点数变可机跑；机跑命令见 references/self-check-gates.md；窄域小任务可省「向」列维持六列，省略时回执的负向占比按人工点数并注明）。**操作列首令牌必须是 `[UI]` 或 `[MACHINE]`**（规则见 E2E 原则第 5 条），全表逐行互斥且无缺省。操作列落笔前先做 **入口实况侦察**：UI 点逐个确认引用的页面/按钮/控件存在、路由可达、文案口径（如大小限制、权限提示）与预期一致；UI 写点还要写 confirm/alert/prompt 文案与保存后回显；机器入口点确认端点/命令存在、鉴权与幂等要求、错误码集合——端点 200 只证明后端在，不证明用户够得着，也不证明契约正确。
6. **判据量化**：预期里的每个模糊词（「明确/正常/合理」）必须进判据表换成量化阈值，或显式标注「人工判定」；AI/LLM 类问题必须 golden set 条目（结构见 `references/ac-id-rules.md`）。
7. **AC-ID 分配**：已有验收域续号；全新功能开新域 `AC-<域>-###`；规则见 `references/ac-id-rules.md`。
8. **门槛标注**：依赖未修缺陷的验收点标 ⛔ 并逐条链接台账条目（缺陷台账为单一事实源，状态不内嵌）；探索性无实现标 ⏭️；两源口径冲突挂起待裁定标 ⏸️（⏸️ 定义=已执行有观察、标准冲突待裁定，与执行侧 §7.3 及 coverage-metrics 口径一致）。台账登记时 **P2 及以上缺陷必须附 test basis 条款引用**，缺失引用降 P3——引用是定级输入，不是事后补注。**台账→验收点全映射闭环（强制）**：生成收尾时把台账全部在管条目逐条对到 ≥1 个验收点（⛔ 挂链 / 复验锚 / 显式 N/A+无 UI 面理由），映射表随交付——台账是实锤失效模式清单，漏挂一条=放弃一次最便宜的深度来源。
9. **环境前置与执行契约骨架成段**：§B 式自检清单（可达/健康/账号/依赖）+ **造数通道盘点表**（见「造数通道盘点」节），GO 才开工；BLOCKED 必须能回溯到通道结论。同时产出**执行契约骨架**（锚 `Execution-Contract`，五字段占位：登记写者/状态唯一事实源/未登记判定清单/任务与下一拍/闸门与红线 + 契约文件路径=报告树 obs/ 推导 + 格式出处指针=simulated-user-acceptance 登记铁律不标版本号）——生成侧只提供骨架与路径，运行时字段由执行侧填写维护，禁止填定值。环境前置必须同时产出「**预期最高可达报告状态**」声明（依据载体能力盘点+窗口包依赖：FINAL/FINAL-WITH-GAPS/INTERIM 上限+理由），写入 §2 与执行契约——无人参与下开局即知本批终点。
10. **完成准则 checklist**：全绿 + 缺陷闭环 + 产物落盘，缺项=任务未完成。
11. **落盘**：`<项目>/tests/plans/<topic>-uat-<date>.md`（骨架见 `templates/task-instruction.md`；全项目/跨块范围用 `templates/project-instruction.md`——全域书**自带各域深度内联**（范围与深度都只由 PRD+十一维推导；「另派块级深化任务书」是全域书之后的增量深化，不是替代、更不是减点理由），在深度内联之上再做它独有的加钻：跨块集成旅程+块间缝隙查漏+全域覆盖对账）。

### 自包含铁律（块级，凌驾六标准之上）
执行所需**一切**信息——操作、预期、判据、回显回合、报告格式、缺陷格式、异常 SOP、产物落盘规范——必须**全部内联**进指令文档。禁止执行期依赖主契约版本文件：`见契约`/`以 V2.x 为准`/`主契约原样要求`/`全表见契约` 类指针一律禁止。原因：块级任务书是**一次性**的，契约一升版，指针即悬空或与新版矛盾——这正是「复用次数决定形态」要防的病。主契约只允许以「AC-ID 命名出处」元数据出现（纯溯源，执行不读它）。**唯一允许的运行时外部依赖只有两个**：① 缺陷台账（缺陷状态单一事实源，⛔ 门槛必须链它）② 环境密钥源（凭据注入），且两者都必须附带**降级路径**（台账不可达→用文档内标注日期的快照决策并报告注明；密钥源不可达→停止并请求操作者提供，禁止猜测）。

**任意 Agent 可执行性（设计基线，凌驾一切）**：交付文档必须内嵌「执行者手册」——如何代入 persona、用什么入口（浏览器页面 / API / CLI）、逐步执行规程、判定纪律、外部依赖降级路径。执行方**无需拥有任何特定技能、记忆或上下文**，任意 AI agent 拿到文档即可开始模拟用户验证。文档中「交给某某技能执行」一类路由语只是本机调度便利，不是文档的依赖；执行方法本身必须在文档内自含。

### 交付物 = 一份指令文档，六条主标准 + 补充标准 7/8/9（详见 `references/executable-standards.md`）
1. 每个验收点有稳定 AC-ID
2. 操作列可直接执行（真实命令/路径，探过可达），且首令牌标明 `[UI]` 或 `[MACHINE]`
3. 预期列可机判（**人能看页面判定**，或按机器入口契约断言：状态码/错误码/幂等/鉴权/字段；主观项显式「人工判定」+核对要点）
4. 环境前置成段（GO 才开工），含造数通道结论
5. ⛔ 门槛逐条链接台账
6. 完成准则 checklist 式

缺一条即返工——交付前逐条自验。

### 交付后
指令文档由执行者按内嵌手册执行；`simulated-user-acceptance` 等通用指南可辅助但不是依赖。执行中任务卡与缺陷流程遵循任务书自带规程；可复用产物回写执行资产；新验收点交维护人。**本技能交付即完成，不跟执行。**

**生成单≠执行单**：用户要「prompt/任务书」时只生成不执行——生成即执行会让未经评审的深度直接固化进执行。派单 prompt 只写纪律/授权/红线，执行知识全在任务书内自包含（防双事实源漂移）；凭据永不入 prompt。**交付回执带七项数字摘要**：总点数/十一维完备（有无 N/A）/D1 占比/负向占比/场景数（含基本/备选/异常流计数）/UI 点数与 UI 主证要求/**需求归宿分布（覆盖/⏭️/⏸️/纯未覆盖四桶机验数，纯未覆盖必须为 0，口径见 references/coverage-metrics.md）**，外加新增点来源统计（PRD 横切/侦察加钻/十一维各多少）与**入口分布（`[UI]`/`[MACHINE]` 各多少）**；BLOCKED 点另报通道结论分布（不存在/不可用/未授权）。占比低于基线时如实标注偏离原因，不粉饰数字。**回执只讲本次交付物本身**：用户问「多少点」就直接报本次任务书的数——不主动给跨文件汇总、版本演进对比、历史计数（历史是留痕不是叙事素材，用户问差异时才给）；来源统计只描述本次各点的出处类别，不扯旧版点数变化。

**收官闸**：final-report.md（终期/收官报告）出具的唯一前置=**未触 0**——§3 主集每一点都有终态落判（✅/部分/❌/⏭️/⏸️，⏭️/⏸️ 必须带理由与处置档）；全域对账（路由/覆盖/台账映射类完整性检查）只是收官的必要条件——**对账差集的 MEASURES 是缺口处置计划，理由填得再满也不改变闸**。未触>0 时按执行侧三态判定（simulated-user-acceptance §8.2 状态判定优先级为唯一权威）：存在未补做 OMITTED 或 UI PASS 证据覆盖<100% → 唯一合法产物=**interim-report-<date>.md**（窗口报告：禁用「终期/收官/final」**称谓类措辞**——载体=标题/章节名与 ⑦ 段判定措辞；⑦ 段结论标注「窗口口径/阶段判定」，第④段明示未触 N 点与 final 暂缓，七段式同构；降级记/闸注记等治理留痕文本不属称谓措辞、豁免）；**例外**：未触>0 且全部 UNREACHABLE/DEFERRED（有尝试证据/接受记录）→ 出 final-report.md 标 FINAL-WITH-GAPS，头部声明未触 N 点、归因、接受人、解除条件；环境闸 NO-GO 属中止记录、不进入 final-report 流程。「收官 GO/带伤 GO」字样仅在未触=0 的报告内合法。任务书模板必须内嵌该闸条款并以字面锚 `Final-Report-Gate` 落字（执行自检可 grep，防窄化解释绕开）。**自主模式终态上限**：无人工裁定通道时终态上限=FINAL-WITH-GAPS、⏸️ 必须带默认处置建议并报告头声明——与执行侧 §8.2 口径一致。

**【定义权归属】**报告三态、产物树、缺陷与证据命名的执行侧定义权归 `simulated-user-acceptance`**（含其 `reference/artifact-conventions.md`）；本节收官闸条款为**生成期快照**——任务书模板内嵌时必须标注执行侧出处（文档+章节指针，不标版本号），执行期条款与本侧冲突时**以执行侧当前版本为准**并在 execution-log 记偏差提交裁定。

## 治理模式（辅）

对既有常驻验收契约（详见 `references/pollution-taxonomy.md`）：
1. **体检**：按 `references/executable-standards.md` 的完整 29119-3/29148 对照矩阵核查（涵盖设计/用例/规程/计划/完成报告，不仅看 AC-ID）；逐项列证据与影响并分级：P1=Shall 级违规/阻塞，P2=必需信息缺失，P3=改进建议。打分不能代替逐项缺陷与证据。
2. **历史污染治理**：内嵌状态快照→台账指针；内联版本标签→清除；执行表历史注记→清除（保留 ⛔/⏭️/⏸️ 执行门槛）；历史唯一合法位置=Changelog。
3. **三件套拆分**：自检脚本/命令手册/端点基线/账号下沉执行层（`<项目>/tests/playbooks|fixtures/`），契约原位留指针。
4. **迁移/新建**：新项目按模板生成四件套空骨架（占位符）——骨架见 `templates/project-skeleton.md`（主契约/执行手册/基线夹具/机读台账四层+层间指针纪律）。

**角色边界**：项目规范正典（如 `<项目>/docs/` 下的验收指令）默认只读——产出=草案/递单，转正走维护人；任务内明确授权除外（在报告注明授权出处）。若另有进度监控/任务管理层，它只负责进度与状态，不代替本技能质量自检或擅自改判；安全授权闸和影响判据真值的澄清闸仍须暂停并处理。

## 纠偏固化纪律

用户指出任何缺口/纠偏时，**默认该缺口本应由生成机制拦住**——处置=当场把该检查项写成机械闸（进 Verification Checklist、十一维核心问题或造假红线），而不是只修本次任务书那一处产物。理由：用户只出意图、不充当检查清单，同一缺口被用户问出第二次=技能学习失败；每次纠偏后自问「这道闸今后怎么必走」。

**删除阀（防范围棘轮，本纪律自身同样受约束）**：新增闸须同批回答两问——①**替代/废弃了哪条旧闸或旧口径**（纯增量须声明适用边界）；②**失效条件**是什么（什么情形下此闸应退役）。每版本发布前做一次 Checklist 退役评审：连续两个版本未被任何返工、缺陷或纠偏引用的闸，进退役候选清单，changelog 记退役去向。闸只增不减=适配范围不受控扩张，与「聚焦测试验收」的本质定位直接冲突。

**变更同步五件套（技能修订收尾闸）**：本技能的任何条款变更，收尾时必查五件——① SKILL.md 正文 ② Verification Checklist ③ references/ 受影响件 ④ templates/ 三件套（task-instruction / project-instruction / project-skeleton）⑤ references/self-check-gates.md。漏同步一件=修订未完成——模板与检查表双源不同步时，按模板生成的任务书过不了自家闸。删除阀两问：①替代了旧的「changelog 记一笔即收尾」隐性口径；②失效条件=技能结构重组（检查表/模板合并或拆分）时按新结构重述本清单。

- [ ] **声称支持矩阵对账**：grep 前端 `accept=`/类型白名单 + PRD 能力清单，列出产品声称支持的每项格式/类型/协议——逐项在任务书里要么有保真验收点要么显式 N/A，禁止只测默认格式
- [ ] **AC 来源充分性审计（生成后强制，模型自检）**：按 `references/provenance-gate.md` 的审计提示，由模型逐点核验：§3 每个 AC 是否有需求/设计源、现行入口源、维度源、探针证据；缺陷锚是否只写 `DEF-xxx`；来源是否引用历史测试文档；覆盖矩阵（当前 PRD 行 / 当前页面-路由-API / D1–D11）是否闭合。**技能不携带可执行脚本，不要求 Python/Node/Shell；外部工具只能是可选辅助。** 旧测试文档不参与生成、不参与对比、不参与新增/删除/crosswalk 分类；点数从当前源覆盖矩阵汇总。审计结论按该文件的 E 段格式输出。
- [ ] **源头新鲜度已核验并写入头部**：生成前 VCS 落后核对实测（commit 短号或快照日期可见）；快照锚必须可复现——短号落笔前须 `git cat-file -e` 验证可解析，死锚禁止写入（死锚实证见 references/self-check-gates.md §8）；离线快照写日期并注明「离线」
- [ ] 深度维度覆盖表十一维全有点或显式 N/A+理由；D3 权限矩阵 🚫 无空洞；**D1 行不得仅由数量核对构成**——解析/展示类对象须有顺序/位置、渲染真显、回填真值、元数据一致中的适用项对号（数量全勾≠内容保真，参考 test-depth-dimensions.md 造假红线）
- [ ] **需求归宿四桶机验**：覆盖对账节需求条目逐条归宿四桶（覆盖/⏭️/⏸️/纯未覆盖），四桶计数机验与头部声明逐桶一致，**纯未覆盖>0=返工**；⏭️ 逐条带声称出处+侦察证据、⏸️ 逐条进冲突登记表，桶位要件缺失视同纯未覆盖（桶定义与算法见 references/coverage-metrics.md §2–§3.1）
- [ ] **深度维度表并集闭合机验**：§3.5 各行 AC-ID 并集（**含同域缩写展开**——`AC-IMP-201~218`、`AC-REC-203/204` 类写法必须展开为全号段再取并）必须等于 §3 主表全集，任一方向差集=返工（漏标/幽灵标注实例与展开算法见 references/coverage-metrics.md §3.2）
- [ ] **页面内容全覆盖机验**：生成期对每管理页输出「页面内容清单」——页上全部交互控件（按钮/筛选器/下拉/翻页/链接/开关）与数据呈现区（表列/字段/卡片/文案区）逐项列明；逐项落 ≥1 验收点或显式 N/A+理由（机验：清单行数=落点行数+N/A 行数，双向差集=返工）。执行期以 G0/巡检核对渲染与清单一致（缺项=清单漏列或产品变更→记偏离）——覆盖粒度从「每页 ≥1 点」提到「页上每个元素有落点」

- [ ] **判据条款级追溯**：§3 每个 AC 的「预期」可逐条回溯到 test basis 条款（PRD/设计/接口规范章节号或条款锚，产品裁定附日期）；无条款可溯的预期标 ⏸️ 或显式「合理期待/行业惯例」（口径见 references/provenance-gate.md「判据条款级追溯」）
- [ ] **实现差异扫描已留痕**：交付含「规格↔实现」双向差集表（规格有实现无→⏸️/实测记录；实现有规格无→补点或 N/A+理由）（口径见 references/source-reconciliation.md「实现差异扫描」）
- [ ] **负向基线核查（P1）**：每个负向用例逐条挂正向基线；无正向基线的点记 ⏭️+通道三选一结论，不得计入负向占比（负向/(正+负) 计算前剔除无基线项）

**G6 任意 Agent 可执行**
- [ ] 任意 Agent 可执行：文档内嵌执行者手册（角色代入/工具要求/执行规程/判定纪律/降级路径），不依赖执行方拥有特定技能
