# 缺陷分类模型与裁定闭环

> 配套 `simulated-user-acceptance` §7。核心口径：**凡「用户拿到的结果与承诺不一致」即缺陷**；根因在代码、设计还是文档只影响分类，不影响是否入库。

## 1 两个字段

| 字段 | 取值 | 回答的问题 |
|---|---|---|
| 类别 | 代码缺陷 / 设计缺陷 / 文档缺陷 / 需求歧义 | 错在哪一层 |
| 定性 | 已定性 / 待定性 | 能不能直接修 |

**已定性**：标准唯一且明确，实现偏离 → 可直接给 P 级、排期修复。
**待定性**：标准多源冲突或缺失 → 先登记，裁定后归类定级；**不得因「未定性」而不入库**。

## 2 类别判定树

按顺序回答，命中即停：

```
Q1 实现是否违反一条唯一且已批准的标准？
   └─ 是 → 代码缺陷（已定性）
Q2 实现是否忠实执行了文档，但文档与用户目标/一致性冲突？
   └─ 是 → 设计缺陷（待定性）
Q3 实现与文档不一致，但实现更符合行业惯例/用户期待？
   └─ 是 → 文档缺陷（待定性，修复=改文档）
Q4 两源都合理，无法判断谁对？
   └─ 是 → 需求歧义（待定性）
```

补充规则：

- 同一问题可同时命中多层（如「文档错 + 代码也错」）→ 以**用户影响最大**的一层为主类别，其余写进备注。
- 「行业惯例」不是唯一依据，需在报告里写明所引惯例或同类产品行为。
- 安全类（明文、越权、注入）即使待定性，风险预判一律为「高」。

## 3 P 级与风险预判

| 定性 | 分级 | 说明 |
|---|---|---|
| 已定性 | P0~P3 | 按项目分级（P0 数据丢失/资金/安全/全模块不可用/不可逆副作用；P1 主流程/结果错误/敏感数据；P2 一般功能/边界；P3 体验/文案） |
| 待定性 | 风险预判：高/中/低 | 不做正式 P 级；高=数据泄露/资金/越权/不可逆；中=主流程受阻但可绕过；低=体验/文案 |

**高风险待定性项必须进入报告「风险接受」清单**，由产品/项目负责人明示接受或列为阻塞；不得因「还没裁定」默认放行（那是把「未定性」当成「没问题」）。

## 4 编号与状态机

```
已定性：DEF-<项目>-<日期>-<三位序号>
待定性：DEF-<项目>-<日期>-P<两位序号>（P=Pending），保留原冲突号交叉引用，如 (C4)
```

状态机：

```
发现 → 待定性（P 编号）
        ├─ 裁定「实现错误」→ 代码缺陷 + P 级 → 已定性
        ├─ 裁定「文档过时」→ 文档缺陷 + P 级 → 已定性（修复=改文档）或关闭
        ├─ 裁定「设计不合理」→ 设计缺陷 + P 级 → 已定性
        └─ 裁定「需求需明确」→ 需求歧义 + 补需求 → 已定性
已定性 → 修复 → 复测 → 关闭（留复测证据）
```

裁定留痕字段：裁定人、裁定日期、依据（文档链接/会议结论）、去向。

## 6 自检闸（报告前逐条过）

| # | 检查项 | 不通过处理 |
|---|---|---|
| 1 | 每个 ⏸️ AC 有对应待定性缺陷 | 补录 |
| 2 | 每条待定性缺陷有源 A/源 B/影响 AC/待裁定问题 | 补齐 |
| 3 | 每条已定性缺陷有 P 级/复现/预期/实际/证据 | 补齐 |
| 4 | 问题总数 = 已定性 + 待定性 | 重算 |
| 5 | 高风险待定性项在风险接受清单 | 补列 |
| 6 | 编号唯一、与台账 AC 双向引用 | 修正 |

## 7 常见误用

| 误用 | 正确做法 |
|---|---|
| 「这是冲突，不算缺陷」 | 冲突是待定性缺陷，必须入库 |
| 「还没裁定，先不记录」 | 先记录待定性，裁定是后续动作 |
| 「文档错了就不算代码问题」 | 文档缺陷也是缺陷，分类为「文档缺陷」 |
| 「待定性不用给风险」 | 必须给风险预判（高/中/低），高风险进风险接受清单 |
| 「已定性才能排期」 | 待定性可排「裁定任务」，裁定后转修复单 |
| 「问题总数只算已定性」 | 总数 = 已定性 + 待定性，双口径并列展示 |
